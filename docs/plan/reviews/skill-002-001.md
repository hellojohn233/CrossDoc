# Review: skill-002

## Findings

- **P1 · resolved** — The user could not bring their own review policy. The key vocabulary was 24 contract terms compiled into `src/core/key-data.ts` and the severity criteria were written for contracts. A user skill under `data/skills/` now carries the domain knowledge, and the review loads it when the documents turn out to belong to its domain.
- **P1 · resolved** — A user skill could have replaced a built-in one. `loadSkills()` reads the built-in root first; a user skill with a built-in name is skipped with a diagnostic, and `PUT /api/skills/:name` answers 409. The reserved names are computed from what is loaded, so there is no second list to keep in sync.
- **P1 · resolved** — The user skill's front-matter was a hazard: a name that does not match the directory breaks the loader's own assertion, and `disable-model-invocation` would put the skill out of reach of the model that is supposed to load it. The server generates the front-matter from the name and the description and never writes that flag.
- **P2 · resolved** — The plan assumed the vocabulary had to become a data file. Checking the code says otherwise: `alignKeyData()` groups by the key string, `isTaxonomyKey()` is a display flag, `keyLabel()` falls back to the key, and `align_key_data` takes an optional `label`. A domain skill lists its keys in its own body and they align like built-in ones. No data file was added.
- **P2 · resolved** — `loadSkills()` scans the user's root only when it is given one, so the verification scripts do not depend on whatever the user has on their machine, and `verify-skills.mjs` stays green whatever is in `data/skills/`.
- **P2 · resolved** — An imported skill is parsed and shown, not saved. A skill changes what the next review does, so the user sees it in the editor and saves it on purpose.
- **P2 · accepted** — The agent chooses the domain itself, by routing on the domain skill's description. A vague description loads the wrong skill. The view says, where the description is written, that the description is what the agent routes on.
- **P2 · accepted** — The vocabulary is not strictly replaced. With a domain skill loaded the agent stops calling `list_key_vocabulary`, but it may still recognise a key it saw in the built-in reference examples, so the domain skill only has to add the keys it cares about. Measured on the example corpus: the domain skill's `payment_days` and `signing_party` were extracted alongside a few contract-shaped ones, and the conflicts the run reported included the payment period and the counterparty, both of which came from the domain skill. Making the replacement strict means the vocabulary has to become data, which this task deliberately avoided.
- **P2 · accepted** — The user's skills are a flat list with no categorization, no tagging, no inheritance, and no template library. The user asked for something small and simple, and the point is that one file is enough.
- **P3 · accepted** — No evaluation set. This task proves the mechanism, not that a given domain skill produces good findings. The evaluation corpus is still open in `docs/plan/backlog.md`.
