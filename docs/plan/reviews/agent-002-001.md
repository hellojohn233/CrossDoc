# Review: agent-002

## Findings

- **P2 · non-blocking** — Result order follows the order of tool calls emitted by the model. CrossDoc's prompt asks the model to issue `parse_document` calls in selected-file order, and Pi Core preserves that call order after concurrent execution. The implementation does not independently reorder results by the original request order if a model emits the calls in a different order. The focused test covers the instructed order. Keep the prompt and test aligned; if request order must be guaranteed regardless of model output, add a deterministic batch boundary in a follow-up.

## Verification

- `npm run typecheck` passed.
- `npm run verify:agent-parallel` passed. It exercises the actual `parseDoc()` parser on multiple PDFs, verifies overlapping calls and a maximum of three active parse-plus-persistence operations, checks result ordering when completion order differs, confirms a malformed PDF returns a per-document error, and verifies successful sources, Markdown, metadata, block IDs, pages, and locations are archived.
- Inspected the installed Pi Agent Core scheduler in `node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js`: parallel tool calls are prepared in assistant call order, executed through `Promise.all`, then emitted in the original call order. A sequential tool in the same batch switches the entire batch to sequential execution, matching the architecture note and the agent prompt's separate parse phase.
- The semaphore transfers each released slot directly to the oldest waiter and decrements the active count only when there is no waiter. Its counter is protected by synchronous JavaScript execution between awaits; the `finally` release also covers parser and persistence failures.
- Parsing and persistence for each document stay inside one semaphore slot. Parsed-document and tool result maps are keyed by document ID, so completion order does not affect each successful document's source blocks or archive contents.

## Conclusion

**pass** — bounded concurrent parsing, partial failure handling, source preservation, and Pi's ordered tool-result behavior meet `agent-002`. The only finding is that selected-file result order depends on the agent following the explicit prompt when constructing its tool-call batch; the verified Pi guarantee is call order, not original request order independent of call order.
