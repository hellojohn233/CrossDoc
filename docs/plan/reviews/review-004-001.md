# Review: review-004

## Findings

- **P1 · resolved** — The review procedure was a fixed call sequence in `src/`, so the steps could not be read, reviewed, or changed without a release. The procedure now lives in three skills under `.agents/skills/`, and one agent reads them and drives the tools.
- **P1 · resolved** — The pipeline and the agent were two implementations of the same job, and only the pipeline was used. The pipeline modules are deleted, and the review now runs on the agent.
- **P1 · resolved** — `report_conflicts` asked the model to hand back the whole conflict list as an argument. The model could not produce it, and the first live run looped on an empty report until it was cancelled. The tool now takes no arguments and reads the previous step's output from the session.
- **P1 · resolved** — The runtime has no turn limit, so any agent step could loop forever. A `beforeToolCall` guard now blocks a tool past the number of times it can produce something new and asks the run to end, and a review is cut short after ten minutes and reported anyway.
- **P1 · resolved** — One verdict with `confidence` returned as a string threw inside the report renderer and lost the whole review, conflicts included. Verdicts are normalized at the boundary, the renderer tolerates a non-numeric score, and a report that cannot be rendered no longer discards the findings.
- **P1 · resolved** — The skill's criteria for a non-conflict were too broad: two documents talking about different parties was treated as a reason to dismiss, so the counterparty difference on the example corpus was waved away. The skill now treats a different counterparty inside one review set as a conflict, and reserves the non-conflict rule for values that answer different questions inside one engagement.
- **P2 · accepted** — The review console showed a progress bar driven by a timer, so it reported steps that had not happened. The console now reads the agent's real tool calls out of the NDJSON stream.
- **P2 · accepted** — The key vocabulary exists once, in `src/core/key-data.ts`. The skill reads it through `list_key_vocabulary` instead of restating it, so the two cannot drift apart.
- **P2 · accepted** — There is no rule fallback any more. A skill needs an agent to read it, so a review without a configured main model returns 503 instead of degrading.

## Verification

- `npm run typecheck` passed.
- `npm run build` passed.
- `npm run verify:review-semantics` passed with sixteen checks: five on the skill files, seven on the pure functions and the verdict normalization, and four on a scripted agent driving the whole run — including one that repeats `report_conflicts` five times and asserts the guard stops the run while keeping the conflicts that were already found.
- The full suite passed: `verify:conflict-diff`, `verify:document-ingest`, `verify:scan-page-blocks`, `verify:storage`, `verify:document-search`, `verify:web-read`, `verify:pdf-page-render`, `verify:pdf-vector-classification`, `verify:agent`, `verify:agent-parallel`.
- A live `POST /api/review` over the three example contracts (MiniMax-M3.1-Flash) returned 4 conflicts, all four verified, in 42s. `report_conflicts` was called once. The agent's tool order was load skill → inspect ×3 → parse ×3 → load skill → vocabulary → align → load skill → verify → report.
- A live Chinese check through the same model found all three planted contradictions — 60 days against 90 days, 人民币 100000 against 150000, 2026 年 3 月 1 日 against 2026 年 4 月 1 日 — each with a Chinese rationale.

## Conclusion

**pass** — the review is now a skill an agent reads, not a pipeline the code runs. The procedure is readable on its own, changing what counts as a conflict is a change to a Markdown file, and the deterministic parts stay pure functions that can be tested without a model. The `/api/review` response body only grew.
